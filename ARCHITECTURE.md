# Architecture

Moira keeps provider-specific behavior at the boundary and passes only validated `QuotaReading` values inward.

```text
Claude response ─> status-line chain ─> minimal atomic cache ─┐
                                                              ├─> typed readings ─> stale merge ─> exhaustion derivation ─> GTK cards
Codex app-server ─> ordered JSON-RPC handshake ─> validator ──┘                                                         │
                                                                                                                        ├─> alert rules ─> NTFY
                                                                                                                        └─> 30s local recompute
```

- `models.py` defines the normalized quota model and rejects invalid percentages or naive timestamps.
- `claude_integration.py` validates structured status-line limits, writes the privacy-minimal cache, and atomically installs/removes a reversible chain around an existing command status line. Full status-line input exists only in process memory while it is passed to the original command.
- `parsers.py` validates Codex percentages, reset epochs, and the exact 10,080-minute weekly duration. Unknown formats are errors, never zeroes.
- `collectors.py` reads the Claude cache and owns the Codex lifecycle. Codex sends `initialize`, validates its response, sends `initialized`, and only then calls `account/rateLimits/read`. A shared 12-second deadline bounds the exchange; exits terminate and reap the app-server process group. Errors never include provider payloads, paths, or stderr.
- `exhaustion.py` is the pure weekly-exhaustion rule: an AVAILABLE weekly reading at ≥100% means exhausted until its weekly reset. STALE, missing, error, or sub-100 readings must not newly establish exhaustion. Derives `ServiceSnapshot` state outside GTK widgets.
- `alerts.py` merges failed refreshes with last successful readings as stale and generates deduplicated threshold, reset, error, exhaustion, and recovery events. The duplicate generic 100% threshold alert is suppressed when an exhaustion event fires. Exhaustion and recovery events are deduplicated once per service/window, independent from thresholds. Alert rules (thresholds/reset/error) are typed per service (`ProviderRules`) and deduplication is per delivery channel: each event yields one key per enabled channel (`<base>:ntfy` / `<base>:native`), a channel key is persisted only after that channel reports success, and legacy unprefixed keys count as delivered on both channels.
- `i18n.py` detects the locale from the environment (LANG/LC_ALL/LC_MESSAGES) and provides French translations with English fallback. No manual selector, no compiled .mo files. Functionally equivalent to gettext.
- `persistence.py` stores versioned JSON configuration (v3) and a small last-known-state cache under XDG directories with mode `0600`. Config v1 → v2 → v3 migrations are additive and preserve every prior setting; v2→v3 copies the legacy global thresholds/reset/error rules into typed per-service `ProviderRules` for both providers. Invalid configuration (bad rules, missing providers, invalid repo) fails closed to defaults. v3 adds separate Claude/Codex collection toggles, native-desktop-notification enablement, compact mode, persisted window size/maximized state, and the update-check repository. Refresh choices are 1, 2, 5, 10, 15, or 30 minutes with a 2-minute default.
- `secrets.py` is the only token boundary and uses libsecret/GNOME Keyring. Tokens never enter JSON state.
- `ntfy.py` validates and constructs requests with the standard library and returns typed sanitized outcomes (`sent`, `invalid configuration`, `network failure`, `timed out`, `server error`) — never raw exceptions, server, topic, token, response body, or paths. The response body read is bounded.
- `desktop.py` resolves the localized XDG desktop directory and idempotently copies/removes the installed desktop entry.
- `ui.py` owns GTK widgets and schedules collectors on worker threads. A refresh guard prevents overlap. Refresh occurs at startup, on focus regain (monotonic debounce), and at the configured interval. Countdowns recompute locally every 30 seconds without collectors. Saving a new interval immediately replaces the GLib timer without restart or duplicates. The History tab (`history_page.py`) uses a genuinely bounded `HistoryReader` with at most one running read and one pending newest request. Results are published through an injected dispatcher (GLib.idle_add) so no callback can update a destroyed page. Stale generations never publish. The chart (`history_chart.py`) uses DrawingArea/Cairo with a shared time axis across all series, dash-pattern differentiation for non-color-only identification, and theme-adaptive background/foreground. The History tab refreshes when it becomes visible and after a successful history write (via `HistoryCoordinator.set_write_success_callback`).

No database, rendered dashboard/terminal scraping, private endpoint, background service, tray, or legacy helper dependency is used. An existing user status-line command remains an independent delegate when Moira chaining is enabled.

## Local history

`history.py` defines typed domain objects separating quota observations (`QuotaObservation`) from optional exact-token observations (`TokenObservation`). Each record carries service, UTC time, source, and a typed `HistoryStatus`: `AVAILABLE_EXACT`, `UNSUPPORTED`, `TEMPORARILY_UNAVAILABLE`, or `INVALID`. Token observations carry `period_start` (logical activity period) and `period_kind` (`day` or migrated `bucket`); ordering and earliest/latest derive from the activity day while `observed_at` remains retrieval provenance. Token counts are signed-int64 bounded; every float, boolean, string, negative, and overflow is rejected.

`history_db.py` stores observations in a stdlib SQLite database at `$XDG_STATE_HOME/moira/history.sqlite3` (mode `0600`). Config and current-state JSON are unchanged. A transactional schema version (`schema_meta` table, currently v4) guards future migrations. Schema v4 uses `token_events` with stable canonical event keys `service:period_kind:period_start` — daily identity is provider/service/period-kind/day, independent of the display source, so a source wording change updates one row. Legacy Package 3/3b source-digest keys are reconciled transactionally to canonical keys (newest wins). The official Codex `summary` is persisted as one typed record per refresh in `codex_summaries` — never duplicated onto daily buckets. Range and retention boundaries are period-kind-aware: daily rows compare the `YYYY-MM-DD` day string, migrated bucket rows the full ISO bucket instant. The complete v4 manifest is validated by content — PRAGMA table_info/index_list/index_info and sqlite_master — never by DDL substrings: exact ordered columns, PK order, affinity, nullability/defaults, index uniqueness/backing table/ordered columns, and the quota replay UNIQUE key `(service, quota_label, bucket, observed_at)` proven through autoindexes (origin `u`). Missing or wrong required non-unique secondary indexes are repaired transactionally; a UNIQUE index occupying a required non-unique slot is never dropped and fails closed. `init_schema` accepts an injectable `V4Contract` so a semantic mismatch can be forced through the production fresh-init path, proving DDL and the version row commit or roll back together. An incomplete database is never labeled v4: a metadata table with no version row is repaired transactionally only when the full v4 manifest validates, otherwise the schema fails closed. Schema v2 removed the v1 `UNIQUE(service, quota_label, bucket)` constraint that destroyed earlier change points; it preserves every distinct percentage or reset transition, including multiple changes inside one 15-minute bucket. Unchanged values retain at most one periodic sample per service/quota/bucket. Exact replay (same `observed_at`) is a no-op. Rows older than 90 days are purged after successful writes using an injected clock. Ordered read APIs cover 24h, 7d, 30d, and 90d with optional service/metric filters, plus a delete-all operation.

History writes are integrated into refresh completion (`_record_history`) via a `HistoryCoordinator` that models capacity as exactly one in-flight batch plus one pending batch. If neither exists, accept the batch and return True. If a batch is in-flight but pending is empty, accept the new pending batch, return True, and do not report saturation. If pending is already occupied, replace it with the newest generation, return False, and latch `backlog saturated`. All transitions are atomic under a single `Condition`. The saturation latch is separate from the latest write diagnostic: while saturation remains unresolved, public status stays `backlog saturated` even when the retained write fails. The sanitized diagnostic is stored internally via `last_write_diagnostic` for the future Diagnostic view. Generation tracking ensures an old in-flight result cannot resolve a newer saturation; only successful completion of the retained or a later generation clears the latch. The coordinator exposes an idempotent `shutdown` connected to the window `close-request` signal. The constructor validates `0 < db_timeout < shutdown_timeout`; defaults are `db_timeout=1.0`, `shutdown_timeout=3.0`. `shutdown(timeout=...)` validates the effective timeout against `db_timeout` before mutating lifecycle state. Lifecycle states: NEW, RUNNING, SHUTTING_DOWN, TERMINATED. Shutdown-before-start transitions directly to TERMINATED and rejects future work. Start-after-terminal-shutdown is a documented no-op. The worker wakes on `Condition.notify_all()` from enqueue and shutdown, not periodic polling. `_thread` is never set to None while the captured thread is still alive. `write_history_safely` returns only a bounded `HistoryWriteResult` with a sanitized diagnostic string (`ok`, `database unavailable`, `schema mismatch`, `invalid observation`, `backlog saturated`). `SchemaVersionError` distinguishes schema-version failures from domain `ValueError` validation failures so that `invalid observation` is returned only for the latter. History failure does not disrupt quota state, display, or alerts. Missing token telemetry does not affect quota collection, display, alerts, or quota-history recording. No raw payloads, prompts, responses, transcript text, private paths, account identifiers, or secrets are stored.

Domain validation is fail-closed: timestamps must be timezone-aware and are normalized to UTC; labels and sources must be non-empty; percentages must be 0–100; token counts must be non-negative signed-int64 integers (booleans, every float, strings, negatives and overflow are rejected). `AVAILABLE_EXACT` requires the exact daily `tokens` total; non-available statuses must not carry any token counts. `QuotaObservation` always exposes `AVAILABLE_EXACT` status.

### History statistics and activity indicators (Package 4)

The History view adds frozen immutable view models (`DailyTokenStats`) and pure GTK-free builders for selected-range daily token indicators. Indicators are computed only from `AVAILABLE_EXACT` rows with `period_kind == "day"`:

- Total tokens, reported-day count, average per reported day, range peak day/count, and peak share (peak ÷ total, as a percentage).
- Denominator: reported exact days only. Missing days are never filled with zero; nothing is extrapolated, annualized, or derived from quota percentages.
- Arithmetic is integer/Decimal with documented rounding: the average is rounded half-up to the nearest integer; the peak share is rounded half-up to one decimal place. Peak ties resolve to the earliest reported day.
- Duplicate (service, day) daily inputs are rejected at the pure aggregation boundary (`prepare_history_view`) — the schema PK makes them impossible, so a duplicate means corrupt input and fails closed instead of double-counting.
- A centralized exact-token capability gate (`_apply_token_capability_policy`) admits only Codex exact rows; impossible exact Claude rows are ignored deterministically — never rendered, summed, or relabeled as supported data — while Claude `UNSUPPORTED` availability notes are preserved.
- Migrated `bucket` events stay in their existing per-kind `TokenSummary` and never contribute to daily averages or peak indicators.
- Zero exact days produce no indicator card at all; one exact day (including an explicitly reported zero-token day) is valid.
- The official Codex summary is displayed separately and explicitly labeled account-wide — lifetime, provider peak, streaks and longest-turn values are never relabeled as selected-range data. Filters and range selectors affect indicators exactly as they affect token rows; Claude remains UNSUPPORTED and shows no token indicators.
- A pure content-state helper (`HistoryContentState`/`derive_content_state`) classifies every result (quota series, token summaries, daily statistics, official summaries, availability). Token-only, summary-only and availability-only results are non-empty History content: the page only shows "no history data" when nothing at all is renderable, and distinguishes it from the narrower "no quota observations in this range" note.

## Package 5: complementary UX

- **Quota cards** show used and remaining percentages (`100 - used`) plus the reset time and a live countdown. Compact mode keeps provider (card heading), status, exhaustion, and reset visible while dropping per-reading progress bars. Tokens are never derived from percentages.
- **Collection toggles**: Claude and Codex are collected independently. A disabled provider is never started, never alerts, never writes fresh history, shows the translated "Disabled" state, and leaves old History readable. Refresh supports zero, one, or two enabled providers.
- **Typed per-service rules**: `Settings.rules` holds `ProviderRules` (thresholds/reset/error) per provider; `evaluate_alerts` reads the rules of the reading's own service. Config v2→v3 copies the legacy global rules into both providers; invalid config fails closed.
- **Native notifications** are delivered via `Gio.Notification` on the `Adw.Application` (never `notify-send`) and are independently enabled from NTFY. Deduplication is per channel: an event yields one key per enabled channel, a key is persisted only after that channel reports success, and one channel never repeats because the other failed. Legacy unprefixed alert keys count as delivered on both channels. Separate NTFY and native test buttons never change dedup state.
- **Diagnostics tab** shows provider state, last/next refresh, History writer status (sanitized coordinator status/lifecycle), channel state, and the app version — no secrets, URLs, topics, tokens, paths, or raw errors. Copy actions exist for quota status, History summary, and diagnostics; copied text is sanitized.
- **Manual update check** (`updates.py`): strict SemVer parsing/comparison against the GitHub repository (`ThibSama/moira` by default), triggered only by the user. Bounded timeout and response size; sanitized outcomes (`up to date`, `update available`, `check failed`, `invalid response`). No startup check, telemetry, token, auto-download, or install.
- **Export and delete-all** (`export.py`): deterministic CSV/JSON export of the selected History range/filter with stable fields, sorted rows, atomic UTF-8 writes (temp + replace, mode 0600), read/write off the GTK thread, and an explicit destination via `Gtk.FileDialog`. Delete-all is confirmed with a destructive `Adw.MessageDialog` and removes only history rows — settings, keyring, and current quota state survive. Both report sanitized outcomes.
- **Geometry**: window size and maximized state persist in the v3 configuration on close. Position is not persisted or restored: GTK 4 / PyGObject exposes no window-position API in this environment and Wayland provides none — stated truthfully, with no X11/shell hacks.

Package 5b corrections: v3 validation is exact-typed (thresholds are non-bool integers 1–100, every switch is an actual boolean, geometry is two positive bounded integers or both null, rules are exactly Claude/Codex, repo is valid); invalid JSON fails closed and migrations never coerce values by truthiness (`"false"` is never enabled). Saving settings explicitly merges the non-editable fields (repository, window size, maximized state) so the form never resets hidden configuration. Export reads every row kind — including availability — with the same clock and the selected 24h/7d/30d/90d boundary. Update checks use strict SemVer 2.0 parsing and precedence (leading zeros, empty identifiers and invalid current versions rejected; build metadata ignored; prerelease ordered). NTFY/native test buttons sanitize every failure path (invalid settings, keyring, executor, Gio) with fixed translated outcomes. Compact exhausted cards render no progress bars while keeping provider, status, used/remaining, exhaustion and reset/countdown.

Package 5c corrections: persisted v3 `rules` is a strict exact-shape contract — it must be an object containing exactly `claude` and `codex`; missing, falsy non-object, empty, incomplete or extra shapes fail closed to a COMPLETE default `Settings` instance (never partial preservation). An explicit sentinel keeps direct in-memory `Settings()` construction ergonomic (rules derived from the legacy globals). SemVer parsing is total and bounded: numeric identifiers longer than 64 digits are rejected (documented safe bound far below Python's int-string conversion limit), so `parse_version` never raises and `check_latest_release` maps oversized inputs to sanitized outcomes. The NTFY test and the manual update check catch synchronous `executor.submit()` failures (stopped/rejecting executor) with fixed translated messages, no raw exception and no dedup-state changes.

Package 5d corrections: the persisted configuration version is decoded before ANY migration — only a non-bool integer 1/2/3 is accepted; boolean, float, string, zero, negative or unsupported explicit versions fail closed to complete defaults with no partial preservation, and the sole legacy rule is a documented versionless file treated as v1. Persisted provider rules use an exact inner shape: each provider object must contain exactly `thresholds`, `reset_alerts` and `error_alerts` (missing fields never fall back to defaults, extra fields are rejected). SemVer grammar is ASCII-only (`[0-9]`, never `\d`) and surrounding whitespace is rejected — non-ASCII decimal digits (Arabic-Indic, full-width) and whitespace-padded tags map to sanitized invalid-response/check-failed outcomes.

## Package 6: agent activity visibility

- `activity.py` is the GTK-free domain: four states (RUNNING, COMPLETED, FAILED, INTERRUPTED), SHA-256-hashed session and turn identities, sanitized bounded model labels, and UTC timestamps. Events are validated fail-closed (malformed, naive, future-skewed, oversized and unknown rejected); replays are idempotent. Each turn transitions independently RUNNING → COMPLETED/FAILED/INTERRUPTED under one provider session: Claude's `prompt_id` and Hermes' `extra.turn_id` name the exact turn (a late event from a previous turn never overwrites a newer turn, and a late start can never reopen a completed turn); without a provider turn id the store derives a deterministic `seq:N` identity from the lifecycle, so legitimate replays never create duplicate turns. A new turn in the same session displays RUNNING; a later failure replaces an earlier success as the most recent terminal state. Out-of-order terminals are rejected; a terminal event for an unknown session is rejected at the session surface and accepted only through the runtime-scoped completion-notifier surface (`record_last`), which can never synthesize RUNNING. The store (`$XDG_STATE_HOME/moira/activity.json`, schema v2) is atomic at mode 0600 with process-safe `fcntl` locking and read-merge-write mutations so concurrent hook processes never lose updates; deletion/corruption/oversized files fail closed to an empty store; turns are pruned per session and sessions per runtime (a running turn/session is never pruned). A v1 file (Package 6c's flat per-session lifecycle) migrates additively on load: each v1 session record is preserved exactly as one legacy turn with the derived `seq:1` identity, states/models/timestamps intact and nothing fabricated (a v1 RUNNING record stays a single RUNNING turn); the documented limitation is that a v1 record carries no per-turn granularity, so it can never be split into finer turns — and malformed v1 shapes fail closed to an empty store rather than migrate partially. The watchdog expires stale RUNNING turns to INTERRUPTED — never to success. `derive_runtime_activity` is a pure display function: spinner while active (count above one, latest sanitized model), then the most recent terminal state for exactly five minutes, then hidden.
- `agent_hooks.py` is the packaged hook entry (`/usr/bin/moira-agent-hook <claude|hermes>`): bounded stdin (≤256 KiB, drained beyond), fixed output (empty stdout, exit 0 on every path), network-free; Claude Code mapping is UserPromptSubmit→RUNNING, Stop→COMPLETED, StopFailure→FAILED, SessionEnd→INTERRUPTED; Hermes mapping is pre_llm_call→RUNNING, post_llm_call→COMPLETED, on_session_end→INTERRUPTED (interrupted wins) or COMPLETED, with a last-event fallback for unknown sessions. Prompts, last-assistant messages, errors, transcripts and paths are read but never stored.
- `claude_integration.py` owns the reversible Claude setup: Moira merges its four lifecycle hook entries into `~/.claude/settings.json` with the exact owned shape (match-all matcher, one command-type hook), preserving unrelated hooks/statusLine/settings byte-for-byte, backing up atomically, installing idempotently, and removing only owned entries — an entry carrying the Moira command outside the owned shape is ambiguous ownership and refuses setup/removal. Legacy pre-6c metadata records are upgraded in place.
- `hermes_hooks.py` probes `hermes --version` and `hermes hooks list` (fail closed to a translated unsupported status), and edits only the top-level `hooks:` block of `$HERMES_HOME/config.yaml` with a dependency-free strict YAML subset parser (event mappings of list-of-mappings with scalar fields; flow styles, block scalars, anchors, compact lists and ambiguous scalars fail closed), round-trip validated before an atomic write; other top-level keys are preserved byte-for-byte.
- `codex_activity.py` uses only the documented app-server protocol: `turn/started` and `turn/completed` notifications (`{threadId, turn}`) mapped per `turn.status` (inProgress→RUNNING, completed/failed/interrupted→terminal); the session identity is the owning thread and the turn identity binds the turn to its thread. `CodexSession` is the real production lifecycle: it starts `codex app-server --stdio` through the documented protocol, owns a thread via `thread/start`, drives real turns via `turn/start` and continuously consumes the real notifications into the ActivityStore, with bounded timeouts and clean process-group termination. A full sequence is valid only for a thread Moira owns; terminal notifications for unowned threads become completion-only last events and never synthesize RUNNING. Codex does not document a way to observe ordinary independent CLI sessions (turn notifications are delivered only to the client subscribed to the thread), so the capability is reported honestly as SESSION_OWNED (Moira-owned app-server sessions only), COMPLETION_ONLY or UNSUPPORTED — never full live monitoring. The capability probe and the Settings test run against an isolated `CODEX_HOME` (no user-state side effects); the Settings test drives the real subprocess protocol boundary and verifies real turn notifications are recorded.
- `agent_integration.py` orchestrates setup/remove/test per runtime: missing binaries or unsupported versions yield translated sanitized states without altering external config; the Test action fires the documented payloads against a throwaway `XDG_STATE_HOME` so fake events never persist and quota-alert dedup is untouched.
- `activity_view.py` is the GTK surface: `ActivityPanel` (heading + Claude Code/Codex CLI/Hermes rows, spinner/icon/state/count/model, present in full and compact modes, hidden when nothing to show) and `ActivityWatcher` — a `Gio.FileMonitor` on the state directory (replacement-safe, deletion/corruption tolerant, bursts coalesced onto the GLib idle loop) plus ONE bounded self-cancelling timer that covers both the watchdog expiry and the exact five-minute hide, released on window shutdown. No polling, `pgrep`, terminal scraping, daemon or tray.

Privacy decisions (activity): only runtime, sanitized model labels, SHA-256 hashed session/turn identities and UTC state timestamps are persisted; prompts, responses, transcripts, paths, raw payloads/errors, accounts and secrets are never stored.

## Package 7a/7b: integration registry and Hermes inventory

- `integrations.py` is the GTK-free domain. It defines immutable types with fail-closed validation — `RuntimeIntegration`, `ProviderIdentity`, `ModelAssignment` (roles `main`/`named`), `CapabilityState` and `IntegrationSnapshot` — using the exact closed state set `IntegrationState` (`available`, `not_configured`, `not_installed`, `unsupported`, `temporarily_unavailable`, `invalid`) and stable bounded slugs/labels. Capability slugs are a closed set (`activity`, `quota_percentage`, `exact_tokens`, `balance`, `cost`); badges carry a state and a sanitized detail, never a numeric value, so unknown cost/balance can never render as zero.
- `run_bounded` is the genuinely bounded subprocess boundary (Package 7b): the child runs in its own process group and its stdout and stderr are read in bounded chunks with independent hard caps (64 KiB each) enforced while it runs. On timeout or overflow the process group is SIGTERM'd, then unconditionally SIGKILL'd after a short grace, and reaped with bounded waits — a SIGTERM-ignoring child or grandchild that inherited the pipes cannot survive, and neither wall time nor retained memory grows with the child's output volume. Failure results carry no output at all (`BoundedResult.outcome` ∈ `ok`/`timeout`/`stdout_overflow`/`stderr_overflow`).
- `probe_hermes_inventory` probes the documented installed Hermes CLI surfaces: `hermes --version` (parse `Hermes Agent vX.Y.Z`), `hermes --help` (prove the `config` subcommand exists before choosing commands), then bounded strict JSON of `hermes config get model --json` (only `default` and `provider` are decoded — the documented `base_url` field is dropped) and `hermes config get providers --json` (only provider slugs and scalar `default_model`/`model`; the `models` list, base URLs, `api_key`/`key_env`, `extra_headers` and TLS material are never read). Exact mappings (Package 7b): absent binary → NOT_INSTALLED; unparseable version/help or a rejected documented command → UNSUPPORTED; malformed or oversized required JSON → INVALID (including a never-ending model output, cut at the cap); timeout/transport/stderr-overflow → TEMPORARILY_UNAVAILABLE; an auxiliary named-provider failure preserves a valid main assignment with fixed sanitized details only. The whole Hermes YAML is never parsed, `.env`/`auth.json` are never read, and inference is never invoked.
- `read_token_status_view` reads the latest exact-token availability through the existing History query path (`query_token_availability` within the 90-day retention window, newest per service) plus whether stored exact token rows or the official Codex summary exist. It is bounded (SQLite timeout), runs off GTK, and never raises: a missing database is reported without creating one, and missing/corrupt History yields the fixed sanitized empty `TokenStatusView`.
- `build_snapshot` assembles the snapshot from the accepted sources only: `agent_integration` capability reports (activity), collector/history quota readings (Claude/Codex quota capabilities, gated by the collection toggles), the history-backed `TokenStatusView` (Codex exact-token capability) and the decoded Hermes inventory (provider/model assignments). Assignments are collapsed deterministically (the main provider wins over a same-slug named entry; named entries colliding with the reserved runtime slugs are dropped; ordering is by role then slug). Badges are independent and truthful: Claude stays percentage-only even if impossible exact rows are injected; the Codex exact-token badge follows the latest typed availability (collection disabled → NOT_CONFIGURED; latest AVAILABLE_EXACT plus stored exact data or an official summary → AVAILABLE; no availability record or a latest AVAILABLE_EXACT without stored data → TEMPORARILY_UNAVAILABLE; TEMPORARILY_UNAVAILABLE/INVALID/UNSUPPORTED attempts map exactly) while old exact totals stay untouched and missing data is never zero; discovered providers (e.g. DeepSeek) report cost as NOT_CONFIGURED with a deferred detail while balance is UNSUPPORTED without a typed local profile (Package 7q: capability support derives ONLY from `ProviderKind`, so a local DeepSeek profile reports `balance=available` — the implemented adapter — every other kind and every profile-less discovered provider stays UNSUPPORTED, and reporting balance support changes no token, cost, usage, quota or activity badge; local profiles feed the snapshot as a bounded immutable sequence using only slug/label/kind — credentials, URLs and raw configuration never enter it).
- `IntegrationCoordinator` is the bounded newest-wins probe coordinator, generic over the probe result: capacity is exactly one in-flight probe plus one pending request (a saturated pending slot is replaced by the newest request), a result publishes only when its generation is the newest accepted generation with no newer request pending and the lifecycle is RUNNING, and `shutdown` is idempotent and bounded (no joins; the probe self-bounds through its subprocess reader). Package 7b hardening: injected submitters and publishers are never invoked while holding the state lock — a synchronous submitter runs the probe inline without deadlocking, a rejecting submitter cannot leave the in-flight slot latched (the slot is cleared and the pending request promoted, recursion bounded to one level), and publishers may re-enter the coordinator; the newest accepted generation claims a publication watermark under the state lock immediately before its publish call so ordering is retained. No polling, daemon thread, process detection or unbounded futures: at most one probe future exists at a time, driven only by page visibility and the explicit page Refresh button. Each probe reads the Hermes inventory AND the history token view under one generation, so a published result is internally consistent; stale History/inventory results never publish.
- `integrations_page.py` is the GTK surface: a scrollable `IntegrationsPage` with an Agents section (the per-runtime Set up / Remove / Test controls moved from the Settings view, behavior unchanged — same handlers, status labels and activity-event suffix) and a Providers and models section rendering sanitized assignments with independent capability badges (EN/FR via `tr`). The page never probes; refreshes route through MainWindow's coordinator, and `shutdown` stops routing and rejects renders.
- Privacy decisions (inventory): only provider slugs, bounded model identifiers, the parsed version and exact states are carried; base URLs, credentials, paths, raw output and exceptions are never persisted, displayed or rendered. No new persisted state or schema is introduced; the snapshot is an in-memory render model refreshed only on page visibility and explicit Refresh.
- `ProviderProfile`/`ProviderKind` (Packages 7d+7e) are the immutable local profile domain: a closed seven-kind set (`deepseek`, `openai_compatible`, `openrouter`, `anthropic`, `openai`, `local`, `custom`), bounded slugs (never `claude`/`codex`/`hermes`), labels, models, strict booleans and an optional sanitized base URL validated by policy: remote kinds require HTTPS and reject literal loopback hosts; `local` accepts only loopback over HTTP/HTTPS; embedded credentials, query strings, fragments, control characters, oversized values, missing hosts and unknown schemes are all rejected, and control characters are rejected in labels, models and Hermes labels. Secrets never live in the profile — the Keyring is the only credential store. `is_valid_profile_slug` is THE strict slug contract (lowercase regex, 64-char bound, reserved-slug rejection) shared by `ProviderProfile` and the Keyring layer.
- Config v4 (Packages 7d+7e): the v1→v2→v3→v4 chain stays additive and every v3 setting is preserved exactly. `provider_profiles` is a slug-keyed object with an exact six-field record shape (`label`, `kind`, `model`, `enabled`, `base_url`, `hermes_label`), strict types and a bounded count (50); `_coerce_profiles` decodes it as a whole — any violation (unknown kind, reserved slug, malformed/oversized record, invalid URL) makes `load_settings` fall back to complete defaults with NO partial profile acceptance. `Settings.validate()` enforces the collection contract and deterministic slug ordering; `save_settings` writes slug-keyed records through the atomic sorted writer. Every whole-config rewrite preserves `provider_profiles`: `MainWindow._read_form()` explicitly carries the loaded collection (and the Keyring items keyed to it) into the new `Settings`.
- `secrets.py` (Packages 7d+7e+7f) generalizes the libsecret schema with slug+purpose-keyed provider credentials (`kind=provider`, `slug`, `purpose=api_key` or `purpose=backup`) while keeping the NTFY API byte-identical. Provider operations are TYPED: `inspect_provider_secret` returns FOUND(value) / ABSENT / UNAVAILABLE (an unavailable vault is never interpreted as absence — blank-credential renames fail closed), and `store/erase_provider_secret` return DONE / UNAVAILABLE / REJECTED (absent-clear is a successful no-op). Invalid or reserved slugs are refused by the shared `is_valid_profile_slug` BEFORE any libsecret call (zero calls). `backup` entries are transient Moira-owned copies of overwritten credentials used by the journal protocol; they are never rendered. - `profile_journal.py` (Packages 7f–7i) is the durable phase journal: a minimal atomic `0600` file under `$XDG_STATE_HOME/moira/profile-tx.json` recording operation kind, validated slugs, phase and sanitized profile metadata ONLY (never credentials, fingerprints, raw exceptions or provider responses). `read_journal` validates EXACTLY: the eight outer keys, concrete types before any default, the nested profile record as EXACTLY seven fields (`slug`, `label`, `kind`, `model`, `enabled`, `base_url`, `hermes_label`) with concrete types — extra fields like `api_key`/`token`/`credential`/`secret` are rejected — and the phase invariants; valid 7f–7h journals still parse. Capability assessment (read-only probes, no message content read):
- No structured surface currently provides exact per-window token counts alongside a matching quota window at refresh time. The Codex `account/usage/read` returns aggregate/lifetime tokens but not a per-window input/output breakdown. The Codex `thread/tokenUsage/updated` notification carries per-turn exact counts but is a per-thread event, not an account-wide refresh.
- Claude's `--print --output-format json` exposes turn-level exact token counts but no per-window account quota token breakdown.
- Therefore, daily exact totals come from the Codex `account/usage/read` `dailyUsageBuckets`; the official `summary` (lifetime, peak day, streaks, longest turn) is persisted as one typed record per refresh and displayed separately from daily totals. Quota history recording proceeds independently. Unsupported/temporarily-unavailable/invalid token states are sanitized secondary notes that never hide older exact data or quota charts.

Privacy decisions:
- Only fresh AVAILABLE readings with percentage and reset_at are stored.
- STALE, error, unavailable, and parse-error readings are never stored.
- No raw payloads, prompts, responses, transcript text, private paths, account identifiers, or secrets are retained.
- Token counts are never estimated or derived from percentages.
