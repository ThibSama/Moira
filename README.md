# Moira

Moira is a compact Ubuntu GTK4/Libadwaita utility for Claude and Codex quotas. It shows Claude five-hour and weekly usage, Codex weekly usage, local reset times, countdowns, refresh state, weekly exhaustion semantics, optional native and NTFY notifications, and a History tab with selectable ranges, exact Codex token statistics, sanitized diagnostics, and CSV/JSON export.

## Quotas

- Claude Code sends structured `rate_limits.five_hour` and `rate_limits.seven_day` data to its configured status-line command after a response. Moira chains the existing command and reads its own minimal cache; it never scrapes the rendered `/usage` screen.
- The installed `codex app-server` read-only `account/rateLimits/read` method returns structured windows. Moira completes the initialize handshake first and accepts only a window declared as exactly 10,080 minutes (seven days). It intentionally does not model or display a Codex five-hour quota.
- Missing data produces **Unavailable**. Invalid provider data produces **Parse error**. When a refresh fails after a success, Moira retains the last successful values as **Stale**.

Provider interfaces can change. Validation fails closed instead of treating changed or missing data as 0%.

## Exact token usage

Exact daily token statistics are computed **only from official Codex account usage** (`codex app-server` `account/usage/read`): typed daily totals, reported days, average per reported day, and range peak day, always labeled per service and range. The official Codex account summary is displayed separately and labeled account-wide; it is never duplicated onto daily buckets. Claude remains percentage-only — Moira never derives, renders, or sums token values for Claude.

## History

The History tab shows quota series with reset transitions and availability states over selectable ranges (**24h, 7d, 30d, 90d**) filtered by service (**All, Claude, Codex**). Exact daily token statistics and the official Codex summary appear when the selected range contains exact Codex data. History is stored locally in a versioned SQLite database (schema **v4**) at `$XDG_STATE_HOME/moira/history.sqlite3` (normally `~/.local/state/moira/history.sqlite3`) and written by a bounded background writer that never blocks the UI. **Delete all history…** (with confirmation) clears the stored rows.

## Weekly exhaustion

An AVAILABLE weekly reading at ≥100% means the service is exhausted until its weekly reset. STALE, missing, error, or sub-100 readings must not newly establish exhaustion. When exhausted:

- **Claude**: the weekly card shows a critical state and the five-hour row is visually disabled. The UI states that weekly exhaustion blocks usage and shows the weekly reset time and countdown, not the five-hour reset. Stored readings remain unchanged.
- **Codex**: the weekly card renders as critical with an unavailable-until-reset message, reset time, and countdown. Moira never adds a Codex five-hour quota.

## Internationalization

Moira detects the locale from the environment (LANG/LC_ALL/LC_MESSAGES) and displays French for French locales with English fallback for all other locales. All visible strings — UI labels, error messages, About dialog, native and NTFY notifications, dates, and countdowns — are localized. No manual language selector is needed.

## Refresh and display

Moira refreshes at startup, on focus regain (with a monotonic debounce and overlap guard), and at a configurable interval. Refresh choices are 1, 2, 5, 10, 15, or 30 minutes. New configurations default to 2 minutes. The v1-to-v2 migration preserves every valid refresh value including 10; the 2-minute default is used only when the value is absent or invalid. Saving a new interval immediately replaces the GLib provider timer without a restart or duplicates. The last and next refresh times are displayed.

Countdowns and next-refresh times are recomputed locally every 30 seconds without collectors. Claude data changes only after a Claude Code response; cache rereads are not fresh provider events.

**Compact mode** keeps provider, status, exhaustion and reset visible while dropping the per-reading progress bars. Quota cards show used/remaining percentages (100 − used) plus a reset countdown.

## Configuration and privacy

Configuration is versioned JSON (**config v3**) at `$XDG_CONFIG_HOME/moira/config.json` (normally `~/.config/moira/config.json`). Last readings and alert deduplication keys are at `$XDG_STATE_HOME/moira/state.json`. Both are written with mode `0600`. Enabling autostart creates `$XDG_CONFIG_HOME/autostart/io.github.moira.QuotaMonitor.desktop` at runtime. Versionless (v1) and v2 configuration files migrate automatically to v3 on load, preserving every user setting; invalid persisted versions fail closed to complete defaults without partial preservation.

Claude's separate `$XDG_STATE_HOME/moira/claude-rate-limits.json` cache contains only `five_hour` and `seven_day` objects. Each has `service`, `percentage`, `reset_epoch`, and `retrieved_at`; status-line input, prompts, transcript paths, workspaces, model names, account data, and secrets are never written by Moira. Chained third-party status-line commands still receive the original input and retain responsibility for their own privacy behavior. The History database holds only typed quota, token, availability, and summary records — never secrets, raw payloads, exceptions, or paths.

## Agent activity

An **Agent activity** panel below the quota cards shows, independently from quotas, whether Claude Code, Codex CLI or Hermes is working: a spinner while a session is active (with a count when more than one session runs and the latest sanitized model label), then the correct symbolic state — completed, failed or interrupted — for exactly five minutes after the last active turn ends, then nothing. Missing terminal events expire through a watchdog to **interrupted**, never to success.

Activity is recorded through Moira-owned, reversible integrations configured in the Integrations view (Set up / Remove / Test per agent):

- **Claude Code**: Moira installs `UserPromptSubmit` (start), `Stop` (completed), `StopFailure` (failed) and `SessionEnd` (interrupted) hook entries alongside the existing status line. Existing hooks and settings are preserved exactly, backups are atomic, and removal deletes only Moira-owned entries — ambiguous ownership is refused instead of guessed. Turn events are correlated per prompt through Claude's documented `prompt_id` base field, so repeated turns inside one session each track independently.
- **Hermes**: a shell-hook adapter installs `pre_llm_call` (start), `post_llm_call` (completed) and `on_session_end` (interrupt/complete) entries in `$HERMES_HOME/config.yaml` (by default `~/.hermes`), merged without a YAML dependency by a strict subset editor that fails closed outside the supported shape; the installed version is probed first and unsupported versions fail closed with a translated status. Turns are correlated through the documented `extra.turn_id`.
- **Codex CLI**: only the documented app-server protocol is used. The Settings **Test** action starts a real Moira-owned `codex app-server --stdio` session against an isolated `CODEX_HOME`, owns a thread through `thread/start`, drives a real turn through `turn/start` and verifies that the real `turn/started` → `turn/completed` notifications are recorded — it is an external integration test, not a synthetic mapping. Codex does not document a way to observe turns from ordinary independent CLI sessions (notifications are delivered only to the client subscribed to the thread), so the capability is reported honestly as **Moira-owned app-server sessions only** — never as full live monitoring of normal CLI sessions. Terminal notifications for unowned threads are recorded as completions and never synthesize RUNNING.

Hooks are network-free, bounded-input (≤256 KiB), fixed-output (empty stdout, exit 0) and nonblocking — a failure never touches the agent. The store at `$XDG_STATE_HOME/moira/activity.json` (mode 0600, atomic, process-safe locking) holds only the runtime, sanitized model labels, SHA-256 hashed session and turn identities and UTC timestamps — never prompts, responses, transcripts, paths, raw errors, accounts or secrets. Repeated turns in one session each keep their own lifecycle (RUNNING → completed/failed/interrupted); a new turn displays RUNNING, a later failure replaces an earlier success as the most recent state, duplicate delivery is idempotent, and a late event from a previous turn never overwrites a newer turn. The panel watches the file live with `Gio.FileMonitor` (bursts coalesced, deletion/corruption tolerated) and bounded self-cancelling timers; there is no polling, `pgrep`, terminal scraping, daemon or tray.

## Integrations

The **Integrations** view is a scrollable page with two sections. **Agents** holds the per-runtime Set up / Remove / Test controls (moved here from Notifications without behavior change). **Providers and models** shows a read-only inventory built from accepted sources: the collector/history quota and token capabilities, the agent-activity capability reports, and the documented installed Hermes CLI surfaces. Hermes displays its current main model and discovered named providers with deterministic duplicate collapsing.

The inventory is read-only in this release: the probe first checks `hermes --version` and `hermes --help`, then reads only the bounded JSON of `hermes config get model --json` (the `default` and `provider` fields) and `hermes config get providers --json` (provider slugs and scalar default models). Each subprocess runs under a genuinely bounded reader — independent hard caps on stdout and stderr enforced while the child runs, with the process group terminated and reaped on overflow or timeout, so memory and wall time never grow with the child's output. It never parses the whole Hermes YAML, never reads `.env` or `auth.json`, never exposes base URLs, credentials, paths or raw output, and never invokes inference. Each provider row shows independent capability badges — activity, quota percentage, exact tokens, balance and cost — with exact states: Claude stays percentage-only, and the Codex exact-token badge follows the latest typed availability observation in History (collection disabled → not configured; latest available with stored exact data or an official summary → available; no availability record, or a latest available observation without stored data, → temporarily unavailable; otherwise the exact state of the latest provider attempt) while old exact totals stay untouched. Unknown cost/balance is shown as a state (never zero), and balance support in the matrix derives only from typed local provider kinds: a DeepSeek profile reports balance as available (the implemented exact adapter), every other kind and every profile-less discovered provider stays unsupported, and reporting balance support changes no token, cost, usage, quota or activity badge. DeepSeek balance is refreshed only through the explicit **Refresh balance** action on DeepSeek profile rows (Edit providers) — the inventory itself makes no `/user/balance` call, and a successful refresh reports exact balances only, never implying token, cost or usage support. Hermes writes and financial units remain deferred to a later release.

**Edit providers** manages local provider profiles and their credentials. Profiles are immutable and provider-neutral: stable slug, display label, closed kind (`deepseek`, `openai_compatible`, `openrouter`, `anthropic`, `openai`, `local`, `custom`), model identifier, enabled flag and an optional sanitized API base URL/Hermes label — persisted additively in config v4 with exact keys, strict booleans and deterministic ordering (every v3 setting is preserved; invalid v4 data falls back without partial acceptance). Per-profile API keys live in GNOME Keyring keyed by slug and purpose (the NTFY token keeps its own item); secrets and fingerprints never enter JSON, the journal, History, activity, diagnostics, exports or logs. Base-URL policy: remote kinds require HTTPS and reject loopback addresses (loopback is reserved for `local`, which accepts only literal loopback hosts over HTTP/HTTPS); embedded credentials, query strings, fragments, control characters and oversized values are rejected, and control characters are rejected in labels, models and Hermes labels too. One strict slug validator (lowercase, bounded, never `claude`/`codex`/`hermes`) is shared by profiles and Keyring items, so invalid slugs never reach libsecret. Profile changes are local only — Moira never writes Hermes configuration, hooks or external files. Blank credential input preserves the existing secret; only an explicit Remove clears it. Saving any other settings never wipes profiles: whole-config rewrites carry the profile collection and its Keyring items through.

Each profile row also has an explicit **Test connection** button — a read-only, bounded provider connection test that verifies the Keyring credential and the configured model against the provider's documented Models endpoint (DeepSeek `GET /models`, OpenAI `GET /v1/models`, OpenRouter `GET /api/v1/models`, Anthropic `GET /v1/models` with `x-api-key` + `anthropic-version`; `openai_compatible` and `local` use a strict `GET <base_url>/models`; `custom` is unsupported). It NEVER calls chat, responses, completions, embeddings, inference, usage, credit or balance endpoints, and generates no tokens. The credential is read from the Keyring immediately before the test and handed to a dedicated child process through a private stdin pipe only — never argv, environment, disk, the journal, diagnostics or logs; the child prints nothing and the outcome is a sanitized state (CONNECTED, NOT_CONFIGURED, AUTH_FAILED, MODEL_NOT_FOUND, UNREACHABLE, TLS_ERROR, RATE_LIMITED, INVALID_RESPONSE, UNSUPPORTED, CANCELLED). The whole run is wall-time bounded with connect/read/total deadlines, independent output caps, a response-body cap, verified TLS, no redirects and no proxy environment; stdin delivery happens INSIDE the total bound — the pipe is nonblocking with partial-write handling in the selector loop, so a child that never reads stdin, a full or reduced-size pipe, or an early stdin close can never block the parent past the deadline (the pipe is closed on every terminal path) — credentials are size-capped before any spawn, and hung descendants are SIGTERM'd then unconditionally SIGKILLed and reaped. The target is resolved EXACTLY ONCE into an immutable family/socktype/proto/sockaddr target; the child creates the socket directly and connects to that validated sockaddr — no second lookup, no `socket.create_connection` — then normalizes and compares `getpeername()` with the validated sockaddr BEFORE any TLS handshake or HTTP header (a mismatch is UNREACHABLE with zero credential transmission); remote kinds reject any local/private/link-local/multicast/reserved address in the resolution (DNS rebinding cannot pass the check and reach a private target) while `local` stays loopback-only; for HTTPS the ORIGINAL hostname is kept for SNI, hostname verification and the Host header, so the peer is verified before any credential leaves. Classification happens BEFORE any Keyring read or spawn: `custom` is UNSUPPORTED regardless of any credential, a missing model or a missing compatible/local base URL is NOT_CONFIGURED, a pre-set cancellation is CANCELLED, and oversized credentials fail closed. 401/403 → AUTH_FAILED, 404 → MODEL_NOT_FOUND, 429 → RATE_LIMITED, a validated 2xx with an exact model-ID match → CONNECTED, malformed/oversized content → INVALID_RESPONSE, transport and TLS failures stay distinct, and an unknown outcome can never become CONNECTED. The Models JSON is parsed strictly: every item must be a dict with exactly one bounded string id, secret/account-bearing keys anywhere (top level or item) are rejected, duplicate or excessive model entries are rejected — a mixed response containing the model plus invalid entries is INVALID_RESPONSE, never CONNECTED. Tests run only on the explicit click, one in-flight plus one newest pending at a time through a single invariant-preserving coordinator: every external submit rechecks shutdown immediately before committing, so close racing a request or a promotion submits nothing (zero Keyring reads and zero spawns after close), and submit rejections (first or promoted) clear the slot, give the rejected request its deterministic rejection completion — the row resets to a translated sanitized failure, never stuck on "Testing…" — and recover iteratively, never recursively, so a request parking during a rejection is still dispatched and `_pending` is never left set while `_inflight` is clear. Every accepted request terminates exactly once: newest-wins replacement terminates the superseded request as translated Cancelled through its own callback (no silent replacement), and the per-row token (widget identity + render epoch + click generation) discards stale completions for edited, renamed, removed or disabled rows and for generations superseded by a newer click on the same row. Editing, renaming, removing, disabling or closing a profile discards any in-flight result. Results are ephemeral — nothing is written to schema, History or any credential metadata. All results are shown as translated statuses — never response bodies, headers, account data, hosts, IPs, paths or exceptions.

DeepSeek profile rows also offer an explicit **Refresh balance** action — the only balance surface in this release. It calls the official read-only `GET https://api.deepseek.com/user/balance` endpoint (Bearer auth) — never the profile URL — and shows EXACT balances with no estimates, conversions, aggregation or persistent history. Only DeepSeek rows show the action: every other kind returns Unsupported BEFORE any Keyring read or network, and a missing credential is Not checked/Not configured before any network. Amounts are parsed with `Decimal` (never float) under a bounded decimal-text contract — signs, exponents, NaN/Infinity, control characters and excessive precision or magnitude are rejected, and the bounded text is preserved for rendering — with Total, Granted and Topped up rendered separately in deterministic currency order (CNY then USD). The payload is validated strictly: the documented top-level and item keys only, a real `is_available` boolean, a non-empty bounded `balance_infos` array, unique CNY/USD entries and exact string amounts; extra, missing, secret/account-bearing or malformed data is INVALID_RESPONSE, and nothing is inferred, summed, rounded, converted or combined. 200 → available/insufficient from `is_available`; 401/403 → authentication failed; 402 → insufficient without invented amounts; 429 → rate limited; 5xx → server error; transport and TLS failures stay distinct; every other status and outcome fails closed. The credential is read from the Keyring immediately before the refresh and handed to the same dedicated-child boundary as the connection test (private stdin pipe only, single validated resolution with a direct connect and a peer check before TLS/headers, verified TLS with SNI/Host, no redirects, no proxy environment, bounded time/body/output and process-group reaping); the child returns only minimal canonical balance JSON through bounded stdout — never raw bodies, headers, hosts, metadata, exceptions or secrets — and prints nothing for non-amount outcomes. The child protocol is crash-safe with no valid-state alias: it runs under a BaseException boundary that terminates through a validated exit code, exit code 1 is not part of the protocol (missing credentials fail before any spawn), an imported `sys.exit(1)`, a KeyboardInterrupt or any runtime/import failure exits a distinct crash code with nothing on stderr, the credential is validated on raw stdin (only the single transport newline is removed — leading/trailing/embedded control characters, empty and oversized keys are rejected), accepted outcomes require byte-for-byte empty stderr and non-amount outcomes byte-for-byte empty stdout, and the child alarm shares one deterministic timeout state with the parent deadline. Results are ephemeral — no config, schema, History, activity, export or log write — a successful refresh implies nothing about token, cost or usage support, and the action reuses the same invariant-preserving coordinator as the connection test (one in-flight plus newest pending, CANCELLED replacement, stale-row guards and exact submit/lookup/spawn/callback cardinalities), starting from a translated Not checked state.

Profile/credential writes are RECOVERABLE transactions across the config file and the Keyring. Before any side effect, a minimal atomic `0600` journal is written under `$XDG_STATE_HOME/moira` recording the operation kind, validated slugs, the phase (`staged` → `staged-secret` → `config-committed`) and sanitized profile metadata only — never credentials, fingerprints or raw exceptions. The journal is validated EXACTLY on read: the key set must be precisely the eight documented fields, every field is type-checked before any default (non-bool integer version, string slugs, real boolean backup flag), the nested profile record must be EXACTLY the seven fields `slug`, `label`, `kind`, `model`, `enabled`, `base_url`, `hermes_label` with concrete types (any extra field — `api_key`, `token`, `credential`, `secret`, arbitrary metadata — is rejected), and the phase invariants hold — valid 7f–7h journals keep parsing. The phase ORDER is persist-before-forward: `staged` (no effect yet) → `staged-secret` (secret staged) → config persistence → `config-committed` (forward) → old-slug clear → mandatory backup drop → clear. Because the forward phase is only written AFTER a successful persist, a failed config persistence can NEVER leave a forward-recovery journal — recovery rolls back or no-ops with no journal rewrite, and a failed cleanup keeps the rollback/no-op journal for an idempotent retry. Recovery chooses ONE direction safely from the actual durable state: a `staged-secret` journal whose profile is already in the config completes FORWARD (a durably committed operation never rolls back); otherwise it rolls the staged secret back (restoring the Moira-owned `backup` Keyring entry). Target lookups are strict: FOUND gets a durable backup before overwrite, ABSENT gets none, UNAVAILABLE fails before any journal or mutation. Backup cleanup after a committed overwrite is MANDATORY: if it fails, the forward journal is kept, a sanitized failure is returned and idempotent recovery removes the backup before clearing the journal — success is never reported while a Moira backup remains, and never while any required journal remains. A failed reload recovery executes no pending mutation; only a later successful reload admits mutations. Keyring lookups are typed (FOUND / ABSENT / UNAVAILABLE): an unavailable vault is never treated as absence, so a blank-credential rename fails closed. All config mutations go through one lock-protected read-merge-write boundary. Startup recovery runs at app start in a bounded, REAPED subprocess on a dedicated single-worker bootstrap executor (wall-time bound, the child arms the same bound itself via SIGALRM): a hung Keyring/config recovery is terminated on timeout and yields a sanitized fail-closed result with every config/profile mutation control disabled; no uninterruptible in-process thread is ever claimed cancelled. Pending mutations are typed deltas applied to the latest committed collection; a rejected submit clears its slot and shows a fixed translated outcome. After shutdown, no new or queued-not-started operation writes; an operation past its durable commit boundary may finish consistently but publishes no callback. The UI shows only `configured` / `not configured` and translated sanitized outcomes, never raw exceptions, URLs or profile JSON.

Inventory probes run off the GTK thread through a bounded newest-wins coordinator with generations (one in-flight probe plus one pending request; stale results never publish; shutdown is bounded and idempotent) and only on page visibility and the explicit page Refresh button — no polling, daemon or unbounded futures. Failures show translated statuses with sanitized diagnostics, never stderr, paths, endpoints or secrets.

## Notifications

The Notifications view configures **native desktop notifications** (via GNOME) and/or an HTTP(S) NTFY server with one topic segment, enabled state, thresholds, reset alerts, error alerts, refresh interval, and login autostart. **Send test notification** performs the explicit live delivery test on the selected channel. A non-empty NTFY token field updates GNOME Keyring; leaving it blank preserves the existing token.

Alert rules are typed **per provider** (config v3): each of Claude and Codex carries its own thresholds, reset alerts, and error alerts, and each provider has its own collection toggle. Disabled providers are never started, never alert, never write fresh history, and show a translated *Disabled* state while old History stays readable.

Exhaustion and recovery events are deduplicated once per service/window and are independent from threshold alerts. Only the generic 100% threshold alert is suppressed when an exhaustion event fires; lower-threshold crossings are governed normally. Threshold notifications require a crossing from below to at-or-above a threshold in the same quota window. Reset and parse/error notifications are deduplicated. NTFY and native channels are deduplicated independently per channel, and a key is persisted only after the channel reports success. Delivery failures are not marked sent and may retry after the next qualifying refresh.

## Diagnostics and copy

A sanitized diagnostics report shows provider state, channels, refresh and History-writer status — with no secrets, server URLs, topics, paths, or raw errors. **Copy** actions export quota status, diagnostics, and History summaries to the clipboard, all sanitized.

## Export

History can be exported as deterministic **CSV or JSON** to a chosen destination (atomic UTF-8 writes, stable column order, rows sorted by observed time). Only sanitized typed fields are exported — never secrets, raw payloads, exceptions, or paths. Failures return a fixed sanitized outcome.

## Manual update checks

The Settings view offers a manual **Check for updates** action that queries the configured repository's latest GitHub release (default `ThibSama/moira`). There is no startup check, no telemetry, no token, and no auto-download or install. Comparison is strict SemVer 2.0; an invalid current version fails the check closed, and every outcome is a fixed sanitized status string.

## Install, upgrade, and uninstall on Ubuntu

Build and install the Debian package:

```sh
./scripts/build-deb.sh
sudo apt install ./dist/moira_0.3.0_all.deb
```

The package depends on Python 3, PyGObject, GTK4, Libadwaita, and libsecret GI. Run `moira` or launch **Moira** from the application menu. Install the same `.deb` on another PC and authenticate each provider CLI separately there.

**Upgrading from 0.2.2**: installing `dist/moira_0.3.0_all.deb` over the previous release upgrades in place. User files are preserved: `~/.config/moira`, `~/.local/state/moira` (including the History database) and the keyring item are untouched, and older v1/v2 configuration files migrate to config v3 automatically on first load.

**Uninstalling** without deleting per-user settings:

```sh
sudo apt remove moira
```

Optional user data can be removed manually from `~/.config/moira` and `~/.local/state/moira`. The NTFY token is a GNOME Keyring item named "Moira NTFY token" and provider API keys are separate Keyring items keyed by profile slug; none are in those directories.

### Claude integration setup

In Notifications, select **Set up Claude integration**. Moira first validates `~/.claude/settings.json`. If a command status line already exists, Moira stores its complete status-line object and substitutes `/usr/bin/moira-claude-statusline`; the wrapper passes the original JSON input to the old command and preserves its output and exit status. Setup writes atomically and creates `settings.json.moira-backup`. **Remove Claude integration** restores only the saved status-line field, preserving unrelated settings changed since setup. Removal refuses to act if another program changed the status line in the meantime.

Complete one minimal Claude response after setup if no recent status-line event exists. Until both structured limits arrive, Moira shows waiting/unavailable (or retains an older successful reading as stale), never 0%.

**Create desktop shortcut** and **Remove desktop shortcut** resolve `XDG_DESKTOP_DIR` through `xdg-user-dir`, copy the packaged launcher, mark it executable, and request GNOME's trusted metadata when `gio` supports it. Both operations are idempotent. If the session has no distinct XDG desktop directory, desktop files are unsupported and Moira explains that instead of guessing an English or localized folder name.

## Troubleshooting

- **Unavailable / CLI not found:** install the official provider CLI and ensure `claude` or `codex` is on the desktop session's `PATH`.
- **No Claude values:** set up the integration, use Claude Code normally, and complete a response. Some account types may not expose both windows.
- **Claude integration conflict:** Moira chains only a valid command-type status line. Inspect the non-secret `statusLine` field and decide which integration should own it; Moira does not overwrite an unknown change.
- **No Codex weekly value:** confirm login and update Codex. Moira requires a rate-limit window declared as exactly seven days.
- **No exact token statistics:** exact daily statistics require official Codex account usage data in the selected range. Claude never produces token values.
- **Keyring error:** ensure GNOME Keyring/libsecret is installed and unlocked. Moira never falls back to a plaintext token.
- **NTFY test fails:** verify the server URL, topic, network, certificate, and token permissions. The token is never included in errors.
- **Desktop shortcut unavailable:** confirm `xdg-user-dir DESKTOP` points to a separate existing directory. Use the application menu if the shell hides desktop files.
- **Stale countdown reaches zero:** refresh again after connectivity/authentication is restored. Stale timestamps remain the last provider-reported values.
- **Weekly exhaustion:** when a weekly reading reaches 100%, Moira blocks usage display and shows the weekly reset countdown. Exhaustion is cleared only by a new AVAILABLE reading below 100% or a new reset window. An expired 100% reading from a past window does not establish exhaustion.
